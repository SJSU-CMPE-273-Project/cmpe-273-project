The SMS adapter and the oracle are built. Here is what they do and what comes next.

A briefing for teammates and the professor: how RelayGuard delivers banking alerts, where the SMS adapter fits, how the oracle proves the system keeps its promises, what is left before the Nov 30 failure review, and how we get the system live on the web.

RelayGuard in one paragraph

Banks send SMS alerts that cannot go wrong: a fraud alert that never arrives, an OTP sent twice, or a "deposit confirmed" that shows up before "deposit pending" all break trust. RelayGuard is the messaging platform between the bank's systems and the customer's phone. It is built to keep four promises even while parts of it are crashing:

No lost messagesEvery alert is delivered, expired on purpose, or parked in the dead-letter queue.
No duplicatesEach event_id reaches the phone at most once, even after retries and replays.
Per-account orderFor one account, message 42 never arrives before message 41.
Bounded latencyp99 time from bank event to phone stays under target.

Toxiproxy sits on purpose between the worker and the adapters. The chaos tests flip it to make a "provider" vanish, slow down or drop connections, and we watch whether the system keeps its four promises.

What the SMS adapter does

It is a small Ruby web service (Sinatra + Puma). The delivery worker sends it one message with POST /send. It passes the message to the SMS "provider" and answers with a status code that tells the worker exactly what to do next. The same code runs twice, as sms_primary and sms_secondary, so the worker has somewhere to fail over to.

The answer is the important part

CodeMeaningWorker should
200 acceptedProvider took the message.Mark it delivered.
503 unavailableTemporary outage (provider down, 5xx, connection refused).Retry with backoff, then fail over to secondary.
504 timeoutProvider too slow.Retry with the same event_id.
422 rejectedPermanent no from the provider.Don't retry. Next channel, or dead-letter.
400 invalidBad request (missing fields).Don't retry. Dead-letter.

Why this matters: if every failure looked the same, the worker would either retry forever on messages that can never succeed, or give up on messages that would have gone through a minute later. Separating "try again later" from "never" is what makes the retry, failover and DLQ logic in Lane 2 possible.

Fault switch for chaos tests

Toxiproxy breaks the network. It can't make a provider answer "rejected", so the adapter has its own switch, changed at runtime with PUT /admin/fault:

ModeBehaviourUsed in
okForward normallyHappy path
failAlways 503T6 provider outage → failover
timeoutHang, then 504Slow provider, client timeouts
rejectAlways 422Permanent failure → next channel / DLQ
flaky503 with a set probabilityRetries and backoff under noise

Guardrails built in

PII masking. Phone numbers and message text never appear in logs. This is a real log line from the test run:

{"event":"send.accepted","event_id":"e-1", "code":200,"ms":1, "recipient":"***0123", "body":"[redacted len=19]"}

The body is not hashed: OTP codes are only 6 digits, so a hash could be reversed by trying all million options.

Idempotency key. event_id is passed to the provider as the Idempotency-Key header. If an acknowledgement is lost and the worker retries, the provider sees the same key and doesn't send twice.

Stateless and locked down. Runs as a non-root user on a read-only filesystem with nothing written to disk. That matches the professor's rule that stateless services use ephemeral storage only.

Simulate mode. Until the oracle exists, the adapter accepts and logs without forwarding, so the Nov 11 happy path is not blocked on me.

How it was tested

18 automated tests pass (status mapping, fault modes, PII never in logs, admin token). I also ran it end to end in Docker by sending messages through Toxiproxy the way the worker will. Both instances returned 200, fail gave 503, reject gave 422, disabling the primary proxy cut the connection and re-enabling it restored delivery. Code is in PR #1.

What the oracle does

The oracle is the referee. It pretends to be the customer's phone and every provider behind it (SMS primary, SMS secondary, push, email). Every message the system delivers lands here, and at the end of a test run it answers one question: did RelayGuard keep its promises? Without it, "we survived the crash" is just a claim. With it, every test produces a pass/fail table.

How a test run works

  1. Reset. The test script starts a fresh run with POST /admin/reset.
  2. Say what was sent. The load generator tells the oracle every message the producers sent (POST /expected). That list is the truth to compare against.
  3. Break things. Chaos scripts kill containers, flip Toxiproxy and set fault rules while traffic flows.
  4. Grade. GET /report compares what was sent with what reached the phone and prints the verdict.

The key idea: catching the duplicate that matters

Real SMS providers remember each message's idempotency key, but each provider keeps its own memory. The oracle copies that behaviour, which lets it tell a harmless retry from a real double text:

safe Retry to the same provider

The worker sends to sms_primary, the acknowledgement gets lost, and it sends again with the same key. The provider recognises the key and doesn't send a second text. The oracle logs it as an "idempotent replay".

duplicate Failover after success

Primary actually delivered, but the worker thought it failed and switched to sms_secondary. Secondary has never seen that key, so it sends too. The customer gets two fraud alerts. The oracle fails no duplicates.

This is exactly the bug that failover logic tends to have, and it's the one T2 and T6 are meant to expose.

Questions you may get

Why doesn't the adapter remove duplicates itself?

It would need to remember every event_id, which means storing state, and then two instances would need to share it. Instead the worker claims each message in the Postgres deliveries table before sending, and the provider gets the same key as Idempotency-Key. Keeping the adapter stateless means it can crash or be killed (test T1) without losing anything.

Why have both Toxiproxy and a fault switch in the adapter?

They break different layers. Toxiproxy simulates the network: the provider is down, slow, or the connection drops. The fault switch simulates the provider's reply: "temporarily busy" (503) versus "this number is invalid, never retry" (422). A real outage can look like either, and the worker has to handle both.

What happens if the primary SMS provider goes down?

The worker gets 503s or refused connections from sms_primary, retries a few times with backoff, then switches to sms_secondary. If both fail it moves to push/email, and only after every channel is exhausted does the message go to the dead-letter queue. Test T6 measures how long that failover takes.

Why 422 and not just 500 for a rejected message?

Status codes in the 4xx range mean "the request itself is the problem, sending it again won't help." Codes in the 5xx range mean "the server had a problem, try again." Using the right family lets the worker decide without parsing error text.

Why doesn't the oracle just read the delivery table in Postgres?

That table is written by the delivery worker, which is the thing under test. If the worker had a bug that marked a message delivered without sending it, its own table would agree with it. The oracle counts only what actually reached it. It reads Postgres for just two states, expired and dead-lettered, because those are deliberate decisions that never reach a phone.

Why does the oracle keep everything in memory?

It's test equipment, not part of the product. Each test run starts with a reset, and the report is saved to docs/results/. Keeping it in memory also keeps it stateless, which fits the storage rule for Kubernetes.

Isn't a replayed DLQ message an ordering violation?

By the strict rule, yes: message 5 arrives after message 6. But that's the intended behaviour of a replay, so the oracle exempts messages the system dead-lettered. Any other message arriving out of order still fails the check.

Did this change the shared Protobuf contract?

No. The adapter's HTTP request is the interface between the worker and the adapter only. I added three optional fields there (account_id, sequence, occurred_at) that the oracle needs, and flagged them to Aaron in the PR.

Getting it live on the web

The professor wants the system running on a one-node Kubernetes cluster that anyone can open in a browser, on free or low-cost hosting. Katherine (Lane 4) owns the deploy; each lane provides the Kubernetes files for its own services. The plan that fits the requirement:

  1. Rent one server. A DigitalOcean droplet running Ubuntu 24.04. Kafka, Temporal, Postgres and Iggy together need roughly 8 GB of RAM. The GitHub Student Developer Pack has historically included DigitalOcean credit, which would cover the semester; check the current offer and price before buying.
  2. Install k3s. A one-command, lightweight Kubernetes made for single machines. It ships with Traefik, which routes web traffic into the cluster.
  3. Publish the images. A GitHub Actions workflow builds each service's Docker image and pushes it to GitHub Container Registry (free for the org), so the server can pull them.
  4. Write the manifests, split by state. Stateless services (adapters, worker, bridge, console) become Deployments with no disk. Postgres, Kafka, Iggy and Temporal become StatefulSets with PersistentVolumeClaims, so their data survives restarts. This split is exactly the professor's storage rule.
  5. Expose only the Ops Console. One public URL (a domain, or a free nip.io name on the server's IP) with HTTPS from Let's Encrypt through cert-manager. Everything else stays internal to the cluster, and the adapter's /admin/fault gets an ADMIN_TOKEN.
  6. Rehearse the failure demo live. Run T1–T7 against the deployed system and show the Ops Console and Grafana while things break and recover.
